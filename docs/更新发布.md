# 小餐馆更新发布

## 客户端流程

从 v1.2.5 开始，设置页“版本与更新”以及托盘菜单提供“检查更新”。v1.2.6 起设置页顶部也提供明显的“检查更新”按钮，点击后自动定位结果，检查和下载期间同步禁用更新操作。这是手动检查，不在启动时请求网络：

1. 读取版本文件并比较 `versionCode` 和 `versionName`。
2. 显示新版本与纯文本更新说明。
3. 用户点击“下载更新”，下载到当前用户数据目录的 `updates` 子目录。
4. 下载过程中计算 SHA-256，失败时丢弃 `.part` 半成品，允许重试。
5. 点击“退出并安装”，确认后再次校验缓存文件，启动安装程序并退出小餐馆。

取消确认不会退出，安装程序启动失败也不退出。退出应用会取消未完成的下载。旧版 v1.2.4 没有更新功能，需要先手动安装 v1.2.5。目录版与便携版使用此入口会安装安装版，不是原地覆盖便携文件；安装后请使用新安装的快捷方式。旧便携版已设置自启动的，应先关闭该自启动，再在安装版重新开启。

`BISTRO_DISABLE_UPDATES=1` 可关闭检查、下载和安装。下载仅限 Windows x64 安装包，目前不支持差分包、断点续传、自动后台检查或静默安装。

## S3 对象布局

端点：`http://124.220.98.33:9000/`

- Bucket：`private`
- 前缀：`bug_restaurant/`
- 版本文件：`http://124.220.98.33:9000/private/bug_restaurant/latest.json`
- 安装包：`http://124.220.98.33:9000/private/bug_restaurant/BugBistro-<versionName>-Setup-x64.exe`

不需要 ListBucket，按确定的对象路径读取。安装包文件名从经过校验的版本号生成，不接受版本文件中的任意 URL 或本地路径。请不要把便携单文件作为更新安装包。

## 版本文件格式

沿用提供的示例结构，示例里的其他产品版本号、说明和哈希不用于本项目：

```json
{
  "versionCode": 1002007,
  "versionName": "1.2.7",
  "sha256": "此处必须是实际安装包的64位十六进制SHA-256，不要直接复制本占位内容",
  "notes": "本版本更新说明，可使用换行。"
}
```

- `versionCode` 是递增的正整数。当前本地值保存在 `package.json`，为 `1002007`；发布下一版必须增加，例如 `1002008`。
- `versionName` 必须是无前导零的稳定版本 `x.y.z`，与 `package.json.version` 和安装包文件名一致，不加 `v` 前缀。
- 新版本的上述两个字段都必须大于本地值，矛盾时拒绝更新，以免误降级。
- `sha256` 是对应 **Setup 安装包** 的哈希，不是便携包、目录版 EXE 或旧安装包的哈希。
- `notes` 是纯文本，最多 12000 字符。整个清单不超过 64 KiB。

## 构建与发布

工作目录：`D:\bug_restaurant\app`。

1. 修改 `package.json` 的 `version`、`versionCode`、`releaseNotes`，同步锁文件版本。
2. 运行 `npm.cmd run pack`。构建成功后自动计算安装包哈希并生成 `release/<版本>/latest.json`。
3. 如仅调整说明，执行 `npm.cmd run update:manifest -- "本次更新说明"`，会针对当前已构建的安装包重新生成清单。
4. **先上传** `release/<版本>/BugBistro-<版本>-Setup-x64.exe` 到 `private/bug_restaurant/`。
5. 确认安装包完整上传且可读取后，**最后上传/替换** `latest.json`，避免客户端发现尚未上传完的新版本。
6. 给 `latest.json` 设置 `Cache-Control: no-cache` 或短缓存；客户端自身也发送禁用缓存请求。版本化安装包可以长期缓存。不要在发布后悄悄替换同名版本的包。
7. 用上一版客户端检查更新、下载、确认安装，验证新版本、配置保留与托盘启动。首次部署 v1.2.5 无法用 v1.2.4 做客户端升级检查，因为旧版没有该功能。

本项目的发布脚本只在本地生成文件，**不上传文件、不更改桶策略、不保存访问密钥**。

## 权限与安全边界

2026-10-27 首次匿名访问上述 `latest.json` 返回 HTTP 403 AccessDenied；管理员调整后复测清单及 v1.2.5 安装包 HEAD 均返回 HTTP 200。该结果仅代表当次可访问，未全量下载线上包核对哈希。客户端遇到权限错误会如实提示，而不是显示“已经是最新版”。

采用静态版本文件方案时，需要发布管理员提供这两个类别对象的匿名 `GetObject` 权限，或改成具有可靠鉴权能力的更新服务。不要把 S3 Access Key / Secret Key 嵌入安装包；不要为了更新把整个 `private` 桶公开。

如果管理员选择开放更新对象，以下仅是可合并到现有桶策略的最小范围示例，**不要覆盖现有策略**：

```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": {"AWS": ["*"]},
    "Action": ["s3:GetObject"],
    "Resource": [
      "arn:aws:s3:::private/bug_restaurant/latest.json",
      "arn:aws:s3:::private/bug_restaurant/BugBistro-*-Setup-x64.exe"
    ]
  }]
}
```

当前端点为 HTTP，哈希和安装包都通过同一未加密通道获取。SHA-256 只能证明安装包与读取到的清单一致，不能证明清单来自可信发布者，也不能防止两者同时被篡改。客户端在设置页及安装确认框中提示这一风险，确认框默认选择取消。正式对外发布建议提供 HTTPS，并进一步采用签名清单或 Windows 代码签名。当前安装包未签名，不应关闭系统安全防护。

安装包限制为 512 MiB；检查超时 10 秒，下载总超时 30 分钟；不跟随 HTTP 重定向。更新服务异常不会修改场景数据、自启动或窗口模式。
